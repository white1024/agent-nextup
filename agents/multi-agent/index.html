Multi-agent collaboration

Split a dependency-ordered spec across several agents, with the engine enforcing the ordering.

Optional — requires the collaboration module.

Got a spec with seven tasks, in waves, with dependencies, and want several agents to split the work? Enable the collaboration module (tick it in the wizard, or turn it on from Project settings with the project open), then:

  1. 01

    1. Give tasks an assignee and dependencies

    Section titled “1. Give tasks an assignee and dependencies”

    A task can carry an assignee and a set of prerequisite tasks. Until every dependency is done, the engine blocks both starting and completing the task — “don’t start a task whose dependencies aren’t finished” is guaranteed by the machine rather than by self-discipline.

  2. 02

    2. Give each agent an identity

    Section titled “2. Give each agent an identity”

    Set NEXTUP_AGENT in each agent’s environment (fe, data, …). Every ledger entry then carries that identity, and the collaboration page’s activity feed shows who did what. In the app’s own terminal, type the name into the Agent identity field beside the launch buttons before you press one. It applies to the next launch, reaches the CLI as NEXTUP_AGENT, and takes precedence over any NEXTUP_AGENT set in a custom agent’s environment; the session’s tab and its row on Agent sessions then carry that name. Leave it blank and the session is anonymous — and an anonymous agent cannot claim tasks.

    Do not put --agent in .mcp.json, even though the hub accepts the flag. That file is normally committed and shared by every worktree, so one machine’s choice would become everyone’s — and the app rewrites the whole nextup entry whenever it deploys or repairs the connection, so the flag would silently disappear. The environment variable is the only durable lever.

  3. 03

    3. Claim vs. assign

    Section titled “3. Claim vs. assign”

    An agent claims a task with claim_task — claims cannot be stolen; claiming an already-claimed task fails. You, or a dispatcher agent, use assign_task to reassign (this can override, and every handover is recorded).

    These two tools only appear in projects with the collaboration module enabled — both in the Tools page authorisation directory and in the agent’s own tool list. A project created with the module already ticked has them authorised from day one; if you switched the module on later, check they are enabled on the Tools page (see Connect an AI agent).

  4. 04

    4. Source code doesn’t collide

    Section titled “4. Source code doesn’t collide”

    What Agent NextUp guarantees is the consistency of tasks and their state. If several agents edit code at the same time, give each one its own git worktree or branch and merge with git at the end. That boundary is written into the collaboration module’s own guide, which ships into the workspace when you enable the module.

    Note

    Identity is self-reported and is used only for auditing and claim semantics. Tool authorisation still follows the allowlist — it does not vary by name.
