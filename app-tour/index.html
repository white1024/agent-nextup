A tour of the app

The Projects home screen and what each page in a workspace does.

Projects (home screen)

Section titled “Projects (home screen)”

Opening the app lands you on Projects: every project you have opened, listed as cards — name, path, template, its domain when it has one, current phase (and which of how many), a completion ring and task count, when it was last opened or last called by an agent, and a “Terminal running” marker if it has a live session. Anything waiting on you — an agent awaiting your authorization, blocked tasks, tasks done but not yet verified — is spelled out in an amber line at the foot of the card. Click a card to enter that project.

Above the cards, the header counts agents at work (sessions in the built-in terminal), things waiting on you and tool calls today across every project; running sessions circle a hub just below it, and the Live column beside the cards lists the newest agent hub calls from all your projects, denials included.

While you are on Projects, the sidebar unfolds the workflow template categories under it — All, each built-in template, and custom templates, each with its project count. Categories with no projects fold behind a single “N more categories” row — click it to list them too; the selected category is never folded away. A “no template” category shows up only if you have legacy workspaces. Click a category to filter.

Projects you have opened stay in the list: they are never pushed out to make room. Hover a card and an × appears in its top-right corner; pressing it asks for confirmation first, then removes the project from the list. That only removes the shortcut — it deletes no files. Use it to clear out entries marked “missing” too.

The toolbar in the top right carries the entry actions. (The first time you use the app, with no projects yet, these appear as entry cards in the middle of the screen instead.)

ActionWhen to use it
Open workspaceThe folder is already an Agent NextUp project (it contains .nextup/)
Initialize new projectStarting a new project from scratch — the most common first step, see Your first project. Opens as a dialog
Adopt legacy projectYou already have a folder in progress (an old codebase, say) and want to add the Agent NextUp management layer. It analyses read-only first, drafts a description and tasks for you to confirm, and never overwrites existing files
Import backupRestore a .zip backup brought from another machine (requires the passphrase that sealed its machine-local data — see Backups)

Wherever the app shows a folder path in full — the dashboard header, a project on the Agent sessions page, the selected member on a team, a delivery’s attachment folder — hover it and two small buttons appear: open the folder in Explorer/Finder, and copy the full path. Long paths are shown with the middle elided, because the tail is the part you recognise; the tooltip and the copy button always carry the whole thing. If the folder has since been moved or deleted, the open button says so instead of doing nothing. On a project card the path is for reading only; hover the card for the whole of it.

Already inside a project and want to switch to another one? Click the current workspace name near the top of the sidebar to open a quick-switch menu, or click All projects above it to go back to the home screen and pick one there (the current project stays open). Switching keeps you where you were: on Tasks in one project, you land on Tasks in the other — a page belonging to a capability module the new project has switched off falls back to its dashboard. The quick-switch menu lists only the most recently opened few — the one you are in is always at the top, and a row at the bottom says how many more there are and takes you to the full list. Nothing is ever dropped from that full list. (Picking a project from the command palette opens it on its dashboard instead.)

Getting around

Section titled “Getting around”

The sidebar comes in two forms. On the cross-project pages it lists Projects, Teams, Agent sessions, Templates and Settings — see the section above for Projects, Teams for teams, The built-in terminal for agent sessions (that page is a console: every session in every project, operable without opening those projects), and Your first project for templates. Inside a project the sidebar lists that project’s own pages and nothing else: All projects at the top (the way back), the workspace switcher, then the pages below. To reach a cross-project page from inside a project, go back through All projects, or use the command palette.

The command palette — Ctrl+K (⌘K on macOS), or the Command palette button at the foot of the sidebar — jumps to any page, switches to another project, or finds a task as you type part of its title. Inside a project it also offers two actions with their own shortcuts: a new task (Ctrl+Shift+N) and recording a decision, progress note or note (Ctrl+Shift+D). While you are typing into the built-in terminal, those keys belong to the CLI running there.

Reading the marks. Status is always a mark beside a word, and each mark means one thing everywhere: a teal square for passed or verified, an amber circle for anything waiting on you (a blocked task, one done but not yet verified, a gate only you can confirm, an agent awaiting your authorization), a violet dot for an agent at work or a task in progress, a hollow square for not yet, and a red warning triangle for something that went wrong.

Pages in a workspace

Section titled “Pages in a workspace”

Everything below is scoped to the current project.

Dashboard

Section titled “Dashboard”

The state of this project on one page. Across the top runs the phase band — every phase as a tile, the current one marked — with a Next step column beside it listing each exit gate still in the way and a button to wherever it gets fixed. Under it, the left column holds the Exit gates card (the checklist, the Advance to next phase button, and this phase’s instructions for the AI) and Recent activity (the latest window of the event ledger — View all in its corner jumps to the Ledger page); the right column holds the Task overview tiles, Milestones, and the box for recording. In a narrow window the columns stack.

You can also record a decision, progress note, or note here. (“Progress” means the wrap-up summary of one round of work; it surfaces in AGENTS.md under “last progress” so the next AI session sees it first.) You can generate a handoff snapshot manually, or press View snapshot to read .nextup/snapshots/latest_handoff.md in full — the first document a new AI session should read. The viewer lets you copy it or regenerate it.

Tasks

Section titled “Tasks”

Create and manage atomic tasks. The status flow is todo → in progress → done; if you get stuck, mark it blocked (a reason is required). The reason is shown with how long ago it was written — nothing re-checks a blocker, so a reason from three weeks ago is a claim to re-test, not a current fact.

Marking a task done only means “claimed done” — there is a separate verification mark, which requires attaching evidence (what you ran, what you saw). If you mark a task done without evidence, the page prompts you to add it. (You can dismiss that prompt permanently, and re-enable it under Settings → General.) Any status change regenerates the handoff snapshot automatically.

Made a mistake or a typo? Press Edit to change the title, description, priority, or tags. Status, verification, archiving, and assignment each have their own controls — editing does not touch them, and does not invalidate an existing verification. Press Delete for tasks you don’t want: after confirmation the task file is gone, but the ledger keeps a record including the title, so you can look up what you deleted. If the task had an artifact bundle (tasks/T-XXXX/), deleting the task deletes the whole bundle with it: proposals, design notes, and spec deltas included. If other tasks depend on this one, the delete is blocked and you are told which tasks depend on it — resolve those dependencies first.

When you have a lot of tasks, use the filter bar at the top (search title/description/ID, filter by status, filter by tag, and sort by ID, priority, or last updated). Clicking a tag chip filters by that tag.

Long-running projects accumulate completed tasks — archiving clears them out. Individual done tasks can be archived, or use Archive verified done to sweep them in one press. Unverified tasks are not swept, so they stay visible as a reminder to add evidence — and a task carrying spec deltas is refused archival altogether until it is verified, since archiving is what folds those deltas into the specs. The same goes for a delta that changed after the task was verified: the verification covers the delta as it stood when someone checked it, so archiving waits until the task is verified again. Sweeps skip such a task and carry on, and the workspace doctor names it. Archiving only hides tasks from the list (tick “Show archived (n)” to see them, and you can un-archive) — the files and history remain.

Verified done tasks are also archived automatically: each time you open the workspace, the engine archives tasks that have been verified-and-done for a set number of days (on by default, a week). The archive row has a switch and a day count — turn it off if you would rather sweep by hand.

Collaboration (only when the collaboration module is enabled)

Section titled “Collaboration (only when the collaboration module is enabled)”

A task board with one column per assignee, including an “unassigned” column; reassign directly on the cards. Click a column heading to fold that column away — the name and count stay, so a board with a dozen assignees can be narrowed to the ones you are working with. Tasks with prerequisites show a lock marker and unlock only when every dependency is done — if you try to start early the engine blocks it and tells you who you are waiting on. Beside the board (under it, in a narrow window) is the agent activity feed: which agent called what, recently.

Specs (only when the specs module is enabled)

Section titled “Specs (only when the specs module is enabled)”

The curated record of what this project does right now. On the left is the list of capability areas (specs/<capability>/spec.md in the workspace root — one file per area, git-trackable); click one to read its Markdown.

Beside them (under them, in a narrower window), the pending folds panel lists in-progress tasks that have written spec deltas (change proposals under tasks/<task-id>/specs/). When a task is verified and then archived, the engine folds its delta into the main spec automatically. If there is a conflict the archive is blocked and the conflicts are listed — fix the delta and archive again. When any folds are waiting, a pending fold(s) button in the page header takes you to the panel.

The page is read-only: specs are just files, so edit them in your editor or hand them to an agent. The folding is what the engine guarantees, at the moment of archiving.

Format. Specs use an OpenSpec-compatible structure: ### Requirement: headings (the trimmed heading text is the requirement’s identity) each normally containing a #### Scenario:. A requirement without one is flagged by the linter but still folds — the structure is advice, not a gate. A task’s delta file uses four sections — ADDED, MODIFIED, REMOVED, RENAMED — and a MODIFIED requirement must be rewritten in full rather than patched. Agents write these with their own file tools; the engine only validates and folds (validate_task_specs checks a delta before you rely on it).

Inbox (only when the teams module is enabled)

Section titled “Inbox (only when the teams module is enabled)”

Deliveries that upstream projects have sent you arrive here as envelopes. Each is one row — who sent it, the opening of their note, an attachment count, and when it arrived — and the row’s View button opens the envelope itself, with the note in full and the attachment list. Turn one into a task in one click, or record it as a decision in the ledger. The list shows the most recent page of them with Show older below; notes have no length limit, so the row clips and the envelope does not.

This is also where you publish your own deliveries: write a note (attachments optional), which packages it into the outbox. On a flow set to send automatically it goes downstream at once; on a manual one it waits for you to send it from Teams — a cross-project page, so go back through All projects or press Ctrl+K (see Teams).

When a new delivery arrives a toast appears in the bottom right and an unread count appears next to “Inbox” in the sidebar. Opening the page clears the count, and the rows that were unread stay marked — with a dot and a heavier sender — for as long as you are on the page, so a badge that says “3” does not leave you hunting for which three. When you open the app, if a different project has unseen deliveries you get a prompt for that too (its View projects button takes you to the projects list, where you can open it) — you don’t have to remember to check when someone sends you something.

A delivery this project’s own agent has already fetched through the hub counts as read: no toast, no count, and its row says Read by name (Read by an agent if the agent gave no name).

Ledger

Section titled “Ledger”

Browse this project’s history. Decisions + progress + notes is the default view (recent activity on the dashboard gets washed out by new events; this doesn’t). You can switch to Agent calls to see only what agents did, or to All events (tasks, gates, and so on). Entries are grouped by date, with “load more” to page backwards — a single view has a display limit, but the complete history always lives in .nextup/ledger.jsonl. You can record decisions, progress, and notes from here too.

Search

Section titled “Search”

Full-text search across the code and documents in your project. Press Build index the first time. The index is a rebuildable derivative — the files are the source of truth.

Tools

Section titled “Tools”

The main column, top to bottom:

  • Workspace doctor: Run checkup is one press to check whether the handoff layer is healthy: broken links, stale handoff, outdated engine curriculum, and so on. Read-only, changes nothing. (Two words this page uses as names: the handoff layer is the set of files an agent reads to take over — AGENTS.md, its CLAUDE.md shell, the operating guide; the engine curriculum is the part of it Agent NextUp itself ships and versions — the guide under nextup_docs/ plus the bundled skills.)
  • Workspace assets: after an Agent NextUp update, upgrade the engine curriculum in your workspace (the operations guide and the general-purpose skills) to the new version in one press. Files you have edited are never touched, and anything overwritten is backed up first.
  • Write tools, granted by capability group or one by one, and read-only tools, which are always allowed (see Connect an AI agent).

A side card — at the top of the page in a narrow window — draws the hub with the write tools you have granted, and carries the Allow agents to reach the hub master switch and the nextup-mcp health card: whether this workspace’s .mcp.json points at a hub the app can find, with Repair connection when it has gone stale.

Terminal

Section titled “Terminal”

Launch an agent CLI (Claude Code, Codex, …) or a plain shell in the project root, without opening a separate terminal window — see The built-in terminal.

Project settings

Section titled “Project settings”

(Workspace-level; only appears when a project is open, at the very bottom of the workspace pages.) Settings that concern only this project: Project info (the name, domain, description, goals and boundaries you gave at creation, all editable here — a rename changes the name the app, the team graph and the handoff show, not the folder; deliveries already sent keep the old name, and the guide files under nextup_docs/ keep it until you upgrade them under Workspace assets on the Tools page, which the page points you to. The title lines of AGENTS.md and CLAUDE.md are yours, so the engine leaves them as they are), capability module switches (such as the collaboration module), the AI takeover layer — another name for the handoff layer above (press Fill missing files to add AGENTS.md, its CLAUDE.md import shell, and the rest of those files to an older workspace in one press), Export backup, and Close current workspace.

Templates (app-level)

Section titled “Templates (app-level)”

Manage workflow templates — inspect the built-ins, and add, edit or delete custom ones. See Your first project.

Settings (app-level)

Section titled “Settings (app-level)”

App-wide settings, reachable without opening a project (like Teams): interface language, appearance theme, Team view (draw the Teams pages as a Star map — the default — or in Orbit; both do the same things, and each remembers its own node positions), interface scale (80–125%, which scales the whole window including the terminal — the terminal’s own font size is separately adjustable), Agent CLIs (which command-line tools the built-in terminal can launch — the preset agent CLIs and the plain shell are read-only, and you can add your own), the reminder and dismissed-hint controls, and About — where Check for updates installs a newer version when you ask (see Install). Settings tied to a specific project (project info, modules, the handoff layer, backups) live under Project settings above.
