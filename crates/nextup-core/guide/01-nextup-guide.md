# 01 — Agent NextUp workspace operating guide (@PROJECT_NAME@)

> Purpose: let any AI session **take this workspace over correctly without the GUI app**.
> Principle: **files are the source of truth** — the app is only a view over them, and a gatekeeper.
> 📐 The **session operating protocol** — what you do on every takeover — is its own short file: [00-protocol.md](00-protocol.md). Read that one every time; read this one when you need the contract.

## 2. Task file format (`tasks/T-XXXX.json`)

```json
{
  "schemaVersion": 1,
  "id": "T-0001",
  "title": "One atomic task that can be accepted on its own",
  "description": "Acceptance criteria, relevant files",
  "status": "todo",
  "priority": 1,
  "tags": [],
  "createdAt": "2026-07-06T00:00:00Z",
  "updatedAt": "2026-07-06T00:00:00Z"
}
```

- `status`: `todo` / `in_progress` / `blocked` / `done`. Marking `blocked` **requires** `"blockedReason": "what it is waiting on"`; remove the field when it unblocks. The engine stamps `blockedAt` alongside it — nothing re-checks a reason, so both takeover surfaces print it next to the reason and mark the section as unchecked. Treat an old one as a claim to re-test, not a fact.
- `priority`: 0 (highest) to 3. `id` is the highest existing number plus one (`T-%04d`).
- Update `updatedAt` (UTC RFC3339) whenever you edit the file.
- Verification fields (optional): `verifiedAt` plus `verifiedNote` (the evidence: what you ran, what you saw). Only a `done` task can be marked, and **any status change invalidates it** — drop both fields when setting a new status. Their absence means unverified.
- `assignee` (optional): who is doing this. Only meaningful with the collab module, which is what surfaces and dispatches on it.
- `dependsOn` (optional): an array of prerequisite task ids. **This task cannot move to in_progress or done until every one of them is done**, and that is enforced by the engine **in every workspace** — the dependency gate is not part of the collab module and does not switch off with it. Use it whenever work has a real prerequisite.
- Archive field (optional): `archived: true` marks a `done` task that has been filed away. The engine **files them automatically** when the workspace opens — verified tasks older than N days, on by default with N = 7, adjustable and switchable on the app's task page. Humans can also file and retrieve by hand in the app; agents do not archive. The file stays where it is and dependency resolution is unaffected. `list_tasks` excludes them by default (pass `includeArchived: true` to see them), and the absence of the field means not archived. Leaving `done` un-archives automatically.

## 3. Event ledger (`.nextup/ledger.jsonl`)

One JSON event per line, **append only**:

```json
{"at":"2026-07-06T08:00:00Z","kind":"decision","message":"Chose approach X, because Y"}
{"at":"2026-07-06T08:05:00Z","kind":"task_status_changed","message":"\"Task title\": todo → done","taskId":"T-0001"}
```

`kind` values: @LEDGER_KINDS@.
**Three channels you may write directly** (every other kind is recorded by the engine during the corresponding operation and must not be fabricated):

| Channel | What it records | Where it surfaces |
|---|---|---|
| `decision` | One directional choice plus its reasoning, within a few lines | Handoff section 4, and "Recent decisions" in AGENTS.md |
| `progress` | A session or phase wrap-up: what was done, where it stopped, where the next round picks up | Top of handoff section 2, and "Last progress" in AGENTS.md |
| `note` | Anything else worth leaving a trace of | The recent-ledger window in handoff section 2 |

**What not to do**: task progress and phase-completion reports are not `decision` entries (use `progress`); long analysis and delivery detail do not belong in the ledger body (put them in memory or `artifacts/` and reference the path from the ledger line); and **a change in actual behaviour belongs in no ledger channel at all** — write it as a spec delta in the task artifact (spec module) and the engine folds it into `specs/` on archive. The ledger records what was chosen and why; the spec records how things now are. The takeover surfaces render only the **first line** of each entry, capped at @SUMMARY_CAP@ characters — the full text is kept in the ledger forever, but nothing past that point reaches the next session. So lead with the conclusion in one short line and put the reasoning on the lines below it. There is only ever that one number: `record_decision` and `record_progress` return a warning on the spot when a first line runs past it, while the entry is still fresh enough to rewrite.

## 4. Workflow harness (`.nextup/workflow.json`)

- Structure: `phases[]` (each with `aiInstructions` and `exitGates`) plus `state` (`currentPhase` / `completed` / `history` / `confirmations`).
- Gate semantics (the engine evaluates these against real state):

| Gate | Passes when |
|---|---|
| `min_tasks(n)` | Total task count >= n |
| `all_tasks_done` | At least one task exists and all are `done` |
| `no_blocked_tasks` | No task is `blocked` |
| `artifact_exists(path)` | The relative path exists inside the workspace |
| `min_decisions(n)` | `decision` events **since entering this phase** >= n |
| `manual_confirm(prompt)` | The user has confirmed it in the app (recorded in `state.confirmations`) |
| `doctor_clean` | The workspace health check (`workspace_doctor`) reports zero errors (warnings do not block) |

- **Advancing**: prefer the hub tool `advance_phase` (§9; it fails outright and lists the reasons when a gate has not passed, with no override). When the tools cannot be reached, ask the user to use the app. If a headless session truly must advance by hand: (1) honestly confirm every gate condition really holds; (2) set `state.currentPhase` to the next phase id and append `{"phase":"…","enteredAt":"…","via":"advance"}` to `state.history`; (3) append a `phase_advanced` entry to the ledger. **Never fake a task status or create a fake file to clear a gate.**
- `manual_confirm` is the user's confirmation and a headless session **may not press it on their behalf**. When one is genuinely needed, ask the user in conversation and record it in the ledger.

## 5. Handoff snapshot (`latest_handoff.md`)

- The engine regenerates it after **every state change** (task created, moved, verified; decision; milestone; advance; lesson). It has four sections: system state / recent ledger (opening with "Last progress") / next steps / blockers and decisions. To refresh it deliberately, use the `generate_handoff` tool (§9) or the app's regenerate button.
- If a headless session (tools unreachable) changed a lot of state, update the file by hand in the same four-section format so the next session — or the app — sees the new state.

## 6. Do not touch

- `.nextup/secrets.enc`: encrypted with a machine-local key and undecryptable off this machine. To migrate, use the app's backup export, which re-encrypts under a passphrase.
- `.nextup/snapshots/` and the content inside the AGENTS.md marker block: engine output, and hand edits get overwritten.
- Existing ledger lines: append-only, history is never rewritten.
- `.nextup/shipped_assets.json` and `.nextup/asset_backups/`: the shipping fingerprints and upgrade backups for the engine material. Editing a fingerprint by hand corrupts the "outdated versus customised" judgement. When the material (this guide, the generic skills in `.agents/skills/` and their `.claude/skills/` copies) is outdated, upgrade it through `upgrade_workspace_assets` (§9) — **agents must not rewrite the material directly**, because that marks it customised and it will never auto-upgrade again. A human customising it deliberately is fine; the engine protects those from being overwritten.

## 7. memory and work_record conventions

- **memory**: when a decision, finding or pitfall is settled in conversation, write a file for it there and then and add its index line to `MEMORY.md`. Never fall into the same hole twice. Update or delete content that goes stale, so a wrong memory does not mislead the next session.
- **work_record**: at the end of the month (or when asked), condense the month's trail into `work_record/YYYY-MM.md` following `_TEMPLATE.md`. The format is load-bearing and a line that matches nothing is dropped silently — but **the tool that renders it is outside this workspace** (the report owner's own toolchain; Agent NextUp ships no renderer). So reproduce the template's shape exactly, ask the owner when you need a rule it does not show, and **do not mark such a task verified on your own** — you cannot run the thing that would prove it. Hand it over and say so. If there was no progress, write "No progress this month" rather than leaving it empty.
- **Shared vocabulary**: when this project coins a term — a word it uses in a narrower or different sense than the rest of the world — give it one memory file: the term, one line of what it means here, and a pointer to wherever the full definition lives. Do not restate the definition; point at it. The payoff is briefing: a sub-agent or a new session that reads the vocabulary file stops guessing what the local words mean, and you stop re-explaining them.

## 9. Hub tools (nextup-mcp)

- `.mcp.json` at the root lets the agent host (Claude Code and similar) spawn `nextup-mcp --workspace .` automatically as a stdio MCP server. **Agent NextUp points that command at the resolved absolute path during init, so no PATH setup is needed** (if the executable cannot be found, there is a one-click repair on the app's tools page). Once connected, route every hub operation through tool calls: the engine keeps the ledger, the handoff snapshot and the AGENTS.md state block in sync, and **editing JSON by hand does not**.
- Read-only tools (@READ_TOOLS@) are always available. Write tools (@WRITE_TOOLS@) are authorised individually (`.nextup/agent_access.json`). A few of them (@GUARDED_TOOLS@) are **off by default in every new workspace**, because they are the gatekeeping itself: declaring your own work verified, advancing a phase past its gates, reaching beyond this workspace, rewriting workspace assets. Ask the user to enable those explicitly. The remaining write tools are pre-authorised in **newly created** workspaces; older ones may still have an entirely empty allowlist (authorisation is per-workspace state and does not change when the material is updated), so **do not assume any of them is available** — call, and handle a refusal. When a call is refused the error explains why; **do not work around it by editing files**. That would succeed and leave no ledger trail; ask the user to authorise you instead. Of these, `claim_task` and `assign_task` belong to the collaboration module, `publish_delivery` / `list_deliveries` / `get_delivery` to the team module, and `list_specs` / `get_spec` / `validate_task_specs` to the spec module. A workspace with a module disabled **does not expose those tools at all** — they appear neither in the tool list nor in the authorisation directory, and the module's own guide file is not shipped either (§1). So the contents of `nextup_docs/modules/` tell you exactly which of these apply here.
- Every tool call, including refused ones, is written to the ledger as `agent_tool_called` so the user can audit it.
- The task-writing tools (`update_task_status` / `set_task_verification` / `claim_task` / `assign_task`) return a **compact result**: the updated task, `handoffRefreshed` (whether the snapshot was regenerated) and `gate` (a one-line exit-gate summary). The full snapshot is not returned on every write — call `generate_handoff` when you actually need it, and do not re-pull the full text during a run of consecutive operations.
- A successful `advance_phase` likewise returns a **compact result**: the phase you just entered, including its aiInstructions (follow them), plus `gate` for the new phase's exit gates in one line. Call `workflow_status` when you need the full picture across all phases.
- A `shipped_asset` warning from `workspace_doctor` means this workspace's engine material is behind the engine. Call `upgrade_workspace_assets` to sync (it touches only untouched items and backs up before overwriting; `dryRun: true` shows the listing first). Items reported as needing human confirmation or as customised are never touched by the tool — relay them to the user to decide item by item on the app's tools page (§6).
- Tool errors are structured JSON `{kind, message, …}`. **Branch on `kind`, never parse the message text.** The kinds you can act on:
@ERROR_KINDS@
  - anything else (`io`, `workspace`, `ipc`, …) is an environment or integrity failure with no agent-side move: report it to the user instead of retrying.
- Forcing an advance (override) and confirming a `manual_confirm` gate are **human-only** — the tool surface has no such capability, so do not go looking for one.

## 10. Do not revisit rejected proposals (the `rejected` field in context.json)

- Rejected proposals live in the `rejected` field of `context.json` (the proposal, the reason and the time). **Check it before proposing**; section 1 of the handoff snapshot also lists them.
- The list holds **two kinds of rejection**, and they do not carry the same weight:
  - **The user ruled it out.** There is exactly one way to reopen it: a **new fact that did not exist when the entry was recorded**, raised **explicitly** as "this is on the do-not-revisit list, but the situation has changed: …", for the user to judge.
  - **You ruled it out** while working (§11 asks you to record these). Weight it as your own past reasoning: a later session may reopen it on better information, but must say what changed and why — silently re-proposing it wastes exactly the analysis the entry exists to preserve.
- **Which of the two an entry is has to be inside the reason you write** — nothing else records it reliably. The `alternative_rejected` ledger event carries an `actor` only when this session declared an identity (`--agent`, or the `NEXTUP_AGENT` environment variable), and the shipped `.mcp.json` sets neither, so an entry with no actor means "nobody said", not "a human decided". Write it into the reason: "(my call during analysis, not confirmed with the user)" or the equivalent.
- Record a rejection the moment it happens (`record_rejected`, with the why — a rejection without a reason will not stop the next session re-proposing it). If you are unsure whether something counts as a formal rejection, ask.
- Rejections are **not** decisions and do not count as such: they get their own ledger kind, so a phase that requires N decisions is not satisfied by recording N things you turned down.

## 11. Judgement rubric (what to do when)

| Situation | Do this | Not this |
|---|---|---|
| The same **error** appears a second time | Stop, write it to memory (one pitfall per file), change approach | Reword it and hit the same wall again |
| The same **approach** fails twice | Change route or ask; do not try a third time | Tweak parameters until it happens to pass |
| Work would touch scope the user never mentioned (schema, deleting files, publishing, a large refactor) | Ask first, with options and a recommendation | Do it "while you are in there" and report afterwards |
| The information is findable (files, git, official docs) | Go and find it | Rely on memory or guess — especially version numbers and API signatures |
| Still unsure after looking | Say "couldn't determine" plus what it affects | Invent a plausible-looking value |

"Recurring error", "retried approach" and "guess" are three **separate counts**. Track them separately — collapsing them into a vague "try again" defeats all three limits.

### Planning mode: when the task is a decision, not a build

Some work has no code in it: choosing between two designs, deciding whether to take on a dependency, working out what a vague request actually means. That is still a task — it needs the same trail as any other, and it needs it **more**, because a decision leaves no artifact behind by default.

Use the primitives you already have; nothing new is required:

- **One task per decision**, its title phrased as the question ("Decide how deliveries are routed"), not as a verb ("routing").
- **`dependsOn`** for decisions that gate work. A task blocked on a decision should say so through the dependency, not through a comment nobody reads — the engine will then refuse to let the dependent task start, which is the point.
- **`record_decision`** when it settles: the choice plus the reasoning, in a few lines.
- **`record_rejected`** for each option you turned down, with the reason. This is the half that gets skipped, and it is the half that pays — an option rejected without a written reason returns as a fresh proposal a few sessions later, and nobody can remember why it died.
- **Deliverable**: if the reasoning is longer than a few lines, put it in `artifacts/` and reference the path. The ledger entry stays short; the analysis has a home.

A decision task is `done` when the choice is recorded and the rejected options are on the record — not when you have finished thinking about it.

## 12. Delegation contract (fill this in when delegating to a sub-agent or an external agent)

Seven fields, and a missing one is a gap: **goal and motivation / scope / non-goals / permitted paths / machine-checkable acceptance criteria / report format / stop conditions**.
**Verification is not self-verification**: acceptance is run by the delegating side or by a fresh context — run the acceptance command, look at the real output — and never taken on the executor's own word.

## 13. Environment facts (memory/env-facts.md)

- The first session creates this file only after **actually checking** with commands (OS and shell, toolchain versions, path conventions, known limits). **Never fill it in from memory**; write `couldn't determine` for anything you cannot check.
- Later sessions spot-check that it still holds before relying on it — environments change and files do not update themselves.

## 15. Retrospective flywheel (`lessons` in rules.json, evidence-based)

- **Evidence-based**: a lesson must cite ledger events that really exist. `record_lesson` takes `text` (the rule itself) and `evidence` — **an array** of event `at` timestamps, even when you are citing only one (`["2026-07-06T08:00:00Z"]`). It validates every entry and refuses a citation that does not resolve. An uncitable lesson is an opinion, and opinions do not go into rules.json.
- **A rule-based floor**: start a retrospective with `post_mortem_candidates` (read-only, no LLM). It derives candidate lessons from hard ledger signals — overrides, blocked tasks, failed tool calls and calls refused for lack of authorisation — with the evidence already attached in the right shape; you rewrite them into actionable rules and then call `record_lesson`. The sessions that most need a retrospective are exactly the ones where free-form LLM reflection produces nothing, and the floor guarantees at least these.
- **How a lesson lives or dies**: when a lesson genuinely does something during the work — steers you away from a mistake, shapes a decision — call `record_lesson_fired`. That is what keeps it alive. One untriggered for 30 days is rotated into `archivedLessons` by `archive_stale_lessons` (**not deleted**: no evidence of effect is not the same as no effect, and deletion is a human's call, §14). The cap is 20; rotate before adding when it is full.
- **Each lesson goes to exactly one destination**, so nothing drifts between two copies:

| Nature of the lesson | Destination |
|---|---|
| An actionable working rule (do this next time) | `lessons` in rules.json (this section) |
| An environment trap (a tool, version or platform quirk) | A memory pitfall file (one per file) |
| A line this project must not cross | `boundaries` in context.json |
| A rejected proposal | `rejected` in context.json (§10) |

## 16. Module guides (only the enabled ones are present)

Each enabled capability module ships its own guide at `nextup_docs/modules/<module>.md` — `collab.md`, `team.md`, `specs.md`, `prime.md`. **Read the ones that are there; there is nothing to read for a module that is off.** The directory listing is the answer to "which modules apply here", and it agrees with the tool list by construction (§9).

If a module is enabled later, its guide appears then. Turning one off leaves the file in place — it simply stops applying, and the tools vanish from the tool list.
