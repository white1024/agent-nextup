# 00 — Session operating protocol (@PROJECT_NAME@)

> **Read this every time you take over.** It is deliberately short, because it is the one file you re-read at the start of every session.
> The contract it refers to — file formats, the ledger, gates, the hub tool surface — lives in [01-nextup-guide.md](01-nextup-guide.md) and is read **on demand**, not every session.
> 🧩 **Modules extend these steps.** If a `modules/` directory sits next to this file, each file in it adds rules to the procedure below — read those once, at your first takeover. A workspace with no modules enabled has no such directory at all; a module switched off later leaves its file behind, and the tools it names stop appearing in your tool list. **The tool list you were handed is the answer**, the files tell you what those tools mean.

1. Read the "Current state" block in AGENTS.md and latest_handoff.md: confirm the current phase, this phase's instructions and the exit gates; read `lessons` in rules.json while you are there (when a lesson genuinely helps during the work, mark it with `record_lesson_fired`, guide §15).
2. Pick the highest-priority task from "Next steps". **If `claim_task` is in your tool list, claim it before you touch anything** (collaboration module, `modules/collab.md`): claiming is what stops two sessions doing the same work, it cannot steal, and a refusal tells you who holds it (`already_claimed`, with `currentAssignee`). Claiming needs a declared identity — if the call answers that it has none, that is a startup flag only the user can set, so say so rather than retrying. Then mark it `in_progress` (prefer the hub tool `update_task_status`, guide §9; edit the file by hand only when the tools cannot be reached, guide §2). **Check the do-not-revisit list (guide §10) before proposing any new direction.**
3. Execute: every output goes in `artifacts/`; if you get stuck, mark the task `blocked` with a reason rather than pushing through. **If `validate_task_specs` is in your tool list, a task that changes how the system behaves is not finished until its spec delta is written** (spec module, `modules/specs.md`): write it under `tasks/<task-id>/specs/`, then call `validate_task_specs` to confirm it will fold. **Call that tool before `done` either way** — investigation, documentation and tidying need no delta, and the empty report it returns for them is you having asked the question rather than never raising it. **You are the only one who knows whether this task changed behaviour**, so the answer has to come from you — a delta that was never written leaves `specs/` quietly out of date.
4. Finish: mark it `done` (the engine regenerates the handoff snapshot, the AGENTS.md state block and the manifest). **done is only a claim of completion**: once you have actually run it and observed correct behaviour, mark it verified with `set_task_verification` and attach the evidence. If you cannot verify it, leave it unverified — the handoff snapshot spells that out, so do not pretend otherwise.
5. Settled decisions and pitfalls: record a `decision` (tool `record_decision`, or write the ledger by hand per guide §3) — **one entry = one directional choice plus its reasoning, within a few lines; task progress and completion reports are not decisions** (channel split in guide §3) — plus a memory file (one fact per file, with an index line). When the user rejects an approach, record it in the do-not-revisit list right then with `record_rejected` (guide §10).
6. Honesty: exit gates are evaluated by the engine against real state. **Never fake file state to get a phase to advance.**
7. Process skills are yours to **invoke proactively** at the right moment; do not wait to be asked. When the user hands you a broad or ambiguous direction, run `/align-scope` **before starting** — settle what "done" means while it is still cheap. Before committing a significant document change (a new document, a rewritten section, an outward-facing README or guide) run `/adversarial-review` (guide §12, the document side of "verification is not self-verification"). When a stretch of work wraps up and you want to know whether the next session can pick it up cleanly, run `/handoff-check`. Always close a session with `/wrap-up` (commit in batches, health check, write the record back — marking a task done is not the end). Record the closing summary with `record_progress`: it surfaces under "Last progress" in the handoff document and is the first thing the next session sees, so put the conclusion on the first line.
   **If your host does not support skills**, the procedures are plain markdown — read and follow `.agents/skills/<name>/SKILL.md` at the same moments.
8. When the user only says "continue": read section 3 of the handoff snapshot, pick one or two of the highest-priority items, say in one sentence what you are about to do and why, then start. Do not re-survey the whole project.
