Teams

Wire several projects into a flow — publish deliveries upstream, route them downstream, optionally automatically.

Once you have several projects, a common shape is “the output of a few research projects feeds one development project”. Teams in the app sidebar (the one beside the Projects page — no project needs to be open) is how you do that. From inside a project, press All projects at the top of its sidebar first, or jump straight there with the command palette (Ctrl+K).

One machine, one graph

A team wires together projects on this machine. The graph itself lives in the app’s folder in your home directory (~/.nextup/teams.json), not inside any project — it does not travel with a project folder, a backup, or git, and Agent NextUp does not sync team graphs between machines. To use a team on another computer, carry it there yourself: export it to a file and import it. Routing moves an envelope file from one project folder to another locally; nothing crosses the network. A received envelope, on the other hand, is an ordinary file inside the downstream project (.nextup/exchange/inbox/ — see the disk contract), so like any workspace file it travels wherever that folder travels, git included. That is a side effect, not a delivery channel: Agent NextUp neither relies on it nor prevents it.

  1. 01

    1. Create a team and connect the flows

    Section titled “1. Create a team and connect the flows”

    Create team asks for a name, then drops you into that team’s flow canvas. (The Teams page has two levels: a card list, then the canvas. Each card draws the team as a small constellation — or orbit, see below — with its members, edges and pending count.)

    Add to team (in the header, or at the foot of the member list) opens Add member project, which picks the projects to manage — when a project joins, Agent NextUp enables its team module automatically, so an “Inbox” appears in its sidebar.

    You can switch that module off again at any time in Project settings → Capability modules, including with deliveries still waiting. It puts the Inbox and the delivery tools away without deleting anything — unsent envelopes included — and switching it back on brings all of them back exactly as they were. When deliveries are waiting, the app names how many went quiet with it.

    Switching off is not disconnecting. Upstream projects can still route deliveries into this workspace while the module is off — the envelopes arrive in the inbox exactly as they always did; you simply do not see them, and neither does an agent, until the module goes back on. Turn it off to put the surface away, not to stop receiving.

    Members are draggable nodes on the canvas (positions are remembered; Tidy up puts everything back in place, and flow lines that span several layers route around intervening nodes rather than being hidden behind them). Each member is a star (a planet on the orbit view) with its name, project path, pending count and when it last received a delivery; the star turns amber while something waits to be sent and goes hollow if the folder is missing. Positions are remembered separately for each view.

    Flows are connected by dragging a line from the small dot on a node’s right edge onto another node (on the orbit view: from the dot beside a planet to another planet). One line connects the two both ways — either project can deliver to the other — and is drawn once, with chevrons pointing both ways (on the orbit view, an arrowhead at each end). The target lights up if it can take the line; a project cannot connect to itself, and two projects already connected both ways won’t drop. To make a line one-way, select either project and remove the direction you do not want in its side panel: each direction is a row of its own, with its own auto-send switch, and the line then carries a single chevron. Drawing a line over a one-way line makes it two-way again. Without a mouse: select a node, then pick a project under Connect to in its side panel and press Connect. Lines may loop: review findings going back to the project that built it, bug reports from a product to the library it builds on — and a one-way line round a longer loop runs underneath the row. A loop never runs by itself: a delivery crosses one edge per publish, and arriving sends nothing on. A project can belong to several teams, and when you route a delivery every downstream across all of them is listed together. Click a line to select it, then press the Remove line button that appears on it (Remove edge on a one-way line).

    The canvas pans and zooms (drag empty space, scroll wheel). The left column always lists members (click one to focus its node; hover the row and a remove button appears on the right, which takes the project out of the team after a confirmation — project files are unaffected). A summary bar sits at the top (members / edges / pending / last delivery), and a minimap in the bottom right.

    The canvas comes in two looks, switched in Settings → General → Team view: Star map (the default — members are stars and flows run left to right) and Orbit (members are planets on one orbit round a hub at the centre, and flows are arcs bending towards it, each ending in an arrowhead). Both show the same team and do the same things, and each keeps its own node positions, so switching back and forth never scrambles the other.

  2. 02

    2. Upstream publishes

    Section titled “2. Upstream publishes”

    The upstream project — you, or its agent — presses Publish on the Inbox page and writes a note (what you are delivering, how the downstream should use it). That gets packaged as an envelope in the outbox (on disk, .nextup/exchange/outbox/). For an agent the same move is the publish_delivery hub tool — one of the gatekeeping tools that ship off by default: authorise it on the Tools page first, or the call is refused (and ledgered, like every denied call).

    Saying who it is for. A delivery goes to every project downstream of its sender unless the sender says otherwise. An agent names the projects it means with the to argument of publish_delivery — only projects this one has a flow to can be named, and the others then never receive it, so nobody downstream has to be told to ignore it. An automatic flow sends only to the projects named; on a manual one the send dialog opens with them already ticked. Publishing from the Inbox page yourself has no such field: on automatic flows it goes to every downstream project at once, and on manual ones you pick in the send dialog (next section).

    Press Attach files to include actual deliverables (code, reports, images — up to 20 files and 50 MiB total). Selected files appear as removable chips and travel downstream with the delivery. You need at least one of note or attachments — an entirely empty delivery cannot be published.

    Files taken from inside the project keep the path they had there, so the downstream sees the same layout your covering note refers to, and two such files may share a name as long as they came from different folders. Files picked from outside the project carry no path — they land under their bare filename, so two outside files with the same name clash and the publish is refused before anything is copied.

    Send the contract along with the work. If you are handing over an implementation, attach the specs it was built against as well. A downstream project holding a system but no contract can describe what it sees; it cannot tell you that anything is wrong. Attach the real files rather than copies made for the occasion — every attachment is a snapshot as of the moment you send it either way, but a spare copy sitting in your own project is a second thing to keep up to date, and one of the two will fall behind.

    On a flow set to send automatically, publishing is sending: there is no waiting window to correct in, so get the content right before you press Publish.

    Published something wrong? Publish the correction and mark it as replacing the earlier envelope. In the app, a “Is this correcting an earlier envelope?” picker appears under the attachment row whenever the outbox holds something still correctable; agents do the same through the hub tool. The old envelope is not deleted: it is listed with a Replaced tag so you can see at a glance which one is stale before you press send, and which one actually goes out stays your call. Auto-send skips replaced envelopes entirely — an automatic line has nobody to read the tag, and a delivery cannot be recalled once it lands. Replacing only works while the original is still waiting; once a delivery has been sent, the downstream copy cannot be recalled, so the picker only offers envelopes you have not sent — and not ones you have already marked, since a second correction should point at the envelope that is actually live.

  3. 03

    3. You route it (or authorise the line in advance)

    Section titled “3. You route it (or authorise the line in advance)”

    Back on the Teams canvas (a cross-project page — from inside a project, go back through All projects or press Ctrl+K), member nodes with something pending show a numeric badge. Click the node to open the side panel, then press Send on an envelope — a dialog lists every downstream (if a project belongs to several teams, all of their downstreams are listed together). All of them are selected by default — unless the publisher named who the envelope is for, in which case only those are ticked; the outbox row says who. Confirm, and the results are listed one by one.

    Flows you trust can have auto-send enabled per edge (a switch on each flow row in the node’s info panel; an All auto checkbox in the header shows and toggles the whole team — empty / indeterminate / checked = all manual / partial / all automatic). Automatic edges are drawn brighter, with two lights running along them and a lightning-bolt mark on the line (a manual edge carries a small chevron instead), so you can see at a glance which lines are automatic. On a two-way line the lights run in each direction that sends automatically. From then on, a delivery on that line is sent the moment it is published — by an agent, through the hub, even while the app is closed; or by you, from the Inbox page. You do not need to open the Teams page or the project for it to go.

    If the downstream cannot be reached at that moment (a drive that is not mounted, say), the delivery stays in the outbox and the app tries again on its own: when it starts, while the publishing project is open (on opening it and on every change in it), and when you open that team on the Teams page. The first failure is announced once, not on every retry. If the same delivery also has flows without auto-send, it is sent along the automatic ones and stays in the outbox until you send the rest — counting only the flows to the projects it was meant for, when its publisher named them.

    You still decide how things flow — the only difference is whether you press send per delivery, authorise that line in advance, or put a project in charge of the team (next section). A member’s own agent can only publish; it never routes. Ledger entries are marked so the cases stay apart: (auto) for an automatic line, (by prime <name>) for a coordinator, and nothing for a send you pressed. The coordinator’s mark needs the coordinator to have an identity — NEXTUP_AGENT in its environment — so an anonymous coordinator’s route reads the same as a send you pressed.

    Once delivered, the entry moves to the collapsible Delivery history panel below the canvas (it opens underneath rather than over the nodes).

  4. 04

    4. Downstream picks it up

    Section titled “4. Downstream picks it up”

    The delivery appears in the downstream project’s Inbox, labelled with its source and the team it came through. Inside the envelope is the note the upstream wrote, and you can turn it into a task in one click — the note becomes the task’s title and the source reference its description — or record it as a decision, which opens a pre-filled draft you can edit before it enters the ledger.

    If the delivery carried attachments, each filename and size is listed below the envelope along with its disk location, which you can copy or open in your file manager — then open the files with your own tools. (The inbox does not preview attachments in-app, which preserves the “content is data, not instructions” boundary.)

    What the downstream agent sees: no standing pointer. The arrival surfaces to you — a toast, an unread badge, the Inbox row. If that project’s own agent opens the envelope with get_delivery first, all three stand down: someone has picked it up, and the Inbox row says which agent read it. In an agent’s takeover path it appears only as history: the arrival is a ledger event, so the handoff snapshot (regenerated the moment a delivery lands) shows a DeliveryReceived line in its recent-activity window until later events push it out. Beyond that transient line there is nothing: the AGENTS.md state block carries no delivery lines, and no protocol step says “check for deliveries”. An agent can read the inbox — the read tools list_deliveries and get_delivery come with the module, and the team module guide the workspace ships covers them — but no standing prompt sends it there. Walking a delivery into the project’s plan is a human move: turn it into a task, or point your agent at the envelope yourself.

    Deliveries are data, not instructions

    Delivery content is another project’s data. When a downstream AI reads it, it is explicitly told this is not an instruction, and the interface holds the same line: links inside an envelope are not clickable and images are not loaded. Acting on it is your call, or the call of whoever turns it into a task.

Letting one project run the team

Section titled “Letting one project run the team”

Once a team has more than a couple of members, routing every delivery and redrawing flows by hand gets repetitive. You can hand that job to a project: press Coordinator in the team header and pick one. Its agent can then read every member’s status, edit the flows, route deliveries, and change the roster — bringing a project in, creating a new one to bring in, or taking one out. That is the work you would otherwise be doing on this canvas.

A coordinator is not a member of the team it runs. It sits above the flow the canvas draws, so it has no node there and no delivery edges, and the member list it reads never includes itself. A project holds one seat per team: you cannot name a member as coordinator, and you cannot add the coordinator as a member. That is also why it needs no edge to hand work down — it can already see every member, and edges exist to move things between projects that cannot see each other.

Naming a coordinator switches on that project’s Team coordination (prime) capability module for you — a coordinator whose module is off would be a badge with no tools behind it.

Naming is itself the grant — for the overview, and only the overview. From the moment you name it, the coordinator can see each member’s summary: phase (or that the member runs ongoing, without phases), task counts, mailbox counts, and the first line of each envelope. That is deliberate. Naming a project as coordinator is the human act of putting it in charge, and a coordinator that cannot see who is busy has been put in charge of nothing.

Everything past the overview waits for you. Reading inside a member, editing the graph, routing, and the sign-off below are each off until you authorise them on that project’s Tools page, one at a time. And a coordinator has no way to give itself any of this: naming one is a human action with no tool behind it, and the naming is also what scopes the authority — to this team, not to every team on the machine.

A coordinator can see what you can see. Task text, decisions, progress notes, the current-state specs — the same material you would read by opening that project yourself. These deeper reads are never silent: each one is written into that member’s own ledger, saying which coordinator did it, so a project can always find out it was read. The summary reads above are the exception — they are counts, they run across every member at once, and they leave no line.

What it cannot do is the work. It never creates a task in another project, changes a status, advances a phase, marks someone’s work verified or confirms a gate you were meant to confirm. Each member has its own ledger, its own permissions you granted it and, if it runs in stages, its own gates; work happens in a project because that project’s agent does it, under those. So a coordinator’s way of getting something done elsewhere is to deliver the material and have someone work there — not to reach in.

The one exception is sign-off: a coordinator can archive a member’s finished task, which is also what folds that task’s spec deltas into that project’s specification. That is the approval step you would otherwise press, and it is a separate permission from reading. It is approval rather than substitution — a task carrying spec deltas is refused until that member’s own agent has verified it.

Two other coordinator actions do touch a member’s folder, though neither is its work: joining a project to a team switches the team module on there, which rewrites that project’s state block and ships it the module’s guide; and routing a delivery writes the envelope into the recipient’s inbox and appends the arrival to its ledger. Both are the same writes the app performs when you press the buttons yourself.

Authority is per team. A project can coordinate one team and be an ordinary member of another, and switching the coordinator off is instant and loses nothing.

Maintenance

Section titled “Maintenance”

If a member project’s folder moves, or its disk isn’t attached, the node turns dashed and is marked missing. Press Find automatically (next to the missing count in the summary bar, or in the node’s info panel): every project carries a stable id inside its own .nextup/ folder, and the app looks for a folder with that id among the paths your teams already know and the projects on this computer’s project list. It fixes the member in every team it belongs to, coordinator seats included, and says what it found. Whatever is still missing gets a Look in a folder… button: pick the folder your projects sit in, and it and the folders directly under it are searched. To point one member at one folder yourself, use Re-link folder in its info panel. Matching is by stable id either way, so picking the wrong folder is rejected.

Renaming a project (Project settings → Project info) carries the new name into every team it belongs to, coordinator seat included. Envelopes already sent keep the name they were sent under — they are a record of what happened.

Removing a member leaves the coordinator alone — it was never one of them. Handing the job to a different project, or clearing it entirely, is the Coordinator button in the team header.

Moving teams to another computer

Section titled “Moving teams to another computer”

Your projects move between computers with git; the team graph does not, because it lives in the app’s folder rather than in any project. You carry it as a file.

Export. On the Teams page, press Export… in the header, tick the teams to take, and save the file (nextup-teams.json by default). Where it goes is up to you — a repo you already sync is the easy choice. Agent NextUp never reads or writes a shared location on its own.

Import. On the other computer, get the projects there first (clone or pull them), then press Import… on the Teams page and pick the file. Before anything changes you see one row per team in it:

  • Not on this computer — ticked, so it is added.
  • Same as here — nothing to do.
  • Differs — you choose Use the file’s or Keep this computer’s. The side that was changed more recently is pre-selected; when there is no telling, this computer’s stays.

Nothing is merged: a team is taken from the file whole, or left as it is. An import never deletes a team — teams on this computer that the file does not list are kept — so a team you deleted on one computer has to be deleted on the other too.

Members are found by id, not by path. The file carries the exporting computer’s paths, which are used as they are where your folders are laid out the same way. Otherwise the app runs Find automatically right after the import, and the result offers Look in a folder… for anything still missing. Finding a folder is not a change to the team, so it never makes one computer’s copy look newer than the other’s.

What the file does not carry. A project’s team module, its coordination module and the tools you authorised for its agent all live inside that project’s .nextup/ folder, so they travel with its git, not with the team file. If you name a coordinator on one computer, commit that project before you switch.

Taking turns between two computers. Pull your projects before you open the app on the other computer, and export again after you change a team. Deliveries are files inside the projects and travel with git as well; with auto-send on, an envelope that reaches both computers unsent can be sent from each of them. Routing itself still happens on whichever computer you are working on.
