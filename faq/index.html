01

Can I edit the files in my project by hand?

Section titled “Can I edit the files in my project by hand?”

Yes. The files are the source of truth — editing a task JSON or context.json by hand is a legitimate operation, and the app reflects it live through its file watcher.

Two kinds of file inside .nextup/ should be left alone, though: rebuildable derivatives (snapshots, indexes), and the append-only event ledger ledger.jsonl (the authoritative audit record).

02

Will the AI mess up my project?

Section titled “Will the AI mess up my project?”

Write tools are authorised by you, by capability group (expandable to individual control). When a new project is created, the everyday recording and flow tools are pre-authorised (create tasks, change status, record decisions/notes/lessons…) so an agent can work as soon as it connects. The gatekeeping tools are off by default — unless you ticked Let agents use every write tool from the start when creating the project — and otherwise you have to open them yourself: marking things verified (set_task_verification, set_milestone_verified), advancing phases (advance_phase), packaging a delivery into this project’s outbox — and, on a flow set to send automatically, delivering it on the spot (publish_delivery), and rewriting workspace assets (upgrade_workspace_assets). How many a given workspace actually shows depends on which capability modules you ticked — publish_delivery arrives with the team module, and a project put in charge of a team brings a further set that reach outside the workspace entirely. reference/mcp-tools marks every one of them.

Every call goes into the ledger. A task an agent marks done stays a claim until it is verified with evidence, and on a project run in stages, phase gates are judged by the engine against real state — an AI cannot declare its own pass.

One boundary to keep in view: the allowlist governs the hub tools. An agent’s own file editor is governed by your agent CLI’s permission system — Agent NextUp deliberately keeps the folder open to hand edits, yours and your agent’s alike. Where the allowlist ends draws the line precisely.

03

I already keep a CLAUDE.md and a TODO list in git. Why an app?

Section titled “I already keep a CLAUDE.md and a TODO list in git. Why an app?”

That setup is what Agent NextUp grew out of, and the medium stays the same — plain files in your folder, under git. What hand-kept markdown cannot give you is the part that has to stay maintained and checked: the handoff snapshot regenerates on every state change instead of when you remember; “done” is a claim until a verification with evidence backs it, and on a project run in stages a phase closes on gates the engine evaluates against real state, not on a checkbox anyone — you or the agent — can tick in a file; every hub call an agent makes lands in an append-only ledger, granted or denied; and the doctor machine-checks the broken links and staleness you would otherwise proofread yourself. If you keep that discipline reliably by hand, you may not need this. The app is for the days you don’t.

04

What should I commit, and what should I ignore?

Section titled “What should I commit, and what should I ignore?”

Commit everything the wizard did not already ignore. Initialisation writes a three-line .nextup/.gitignore covering the machine-local files — secrets.enc (sealed by this machine’s key), index.sqlite (a rebuildable search index), .mutex (a transient lock) — and everything else is designed to travel with the repo: tasks, the ledger, snapshots, AGENTS.md, specs. The ledger and the current snapshot are the project’s history and its handoff — exactly the things you want in version control.

One exception if the same project is worked on from more than one machine: .mcp.json holds the absolute path of the hub on the machine that wrote it, so committing it hands every other machine a path that does not exist there. Either leave .mcp.json out of version control (each machine then presses Repair connection on the Tools page once after cloning), or keep committing it and repair after pulling on the other machine — the workspace doctor flags the mismatch either way. On a single machine, commit it like everything else.

05

I switched machines, or haven’t touched a project in ages. How do I pick it back up?

Section titled “I switched machines, or haven’t touched a project in ages. How do I pick it back up?”

Read the handoff snapshot — press View snapshot on the dashboard, or open .nextup/snapshots/latest_handoff.md directly. Where things stand (and, on a project run in stages, which phase you’re in), how far you got, and what comes next are all in there.

06

Will the project documentation rot (broken links, stale information)?

Section titled “Will the project documentation rot (broken links, stale information)?”

The Tools page has a workspace doctor that machine-checks in one press: broken links, stale handoff, missing handoff files, and so on. Error-level problems also block phase advances, if the template has a doctor gate.

07

Why doesn’t my project show phases?

Section titled “Why doesn’t my project show phases?”

Because it runs ongoing — what a new project does unless you tick This project has clear stages and an end point when you create it. Most projects are a stream of work with no finish line, so an ongoing project has no phases to advance and no exit gates: tasks come in and get done one by one, and the dashboard shows the template’s Working instructions — the same method, written as the moments to reach for each skill — where a staged project shows its gates.

If your project does have clear stages, turn on Staged under Project settings → Workflow. The switch works in both directions, only you can flip it (agents have no tool for it), and each switch is written to the ledger. Switching back to staged picks up at the phase the project had reached — with that phase’s decision count and manual confirmations starting over — and the phase history is kept.
